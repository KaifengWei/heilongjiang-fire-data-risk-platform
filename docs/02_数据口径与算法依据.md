# 数据口径与算法依据

平台正式定位与文件验收规则以 `05_平台边界与文件提交规范.md` 为准；风险或关注等级以 `06_风险评级方法与口径.md` 为准。

## 1. 三项核心指标

| 页面字段 | 数据来源 | 计算方法 | 不能解释成什么 |
|---|---|---|---|
| 主动火点观测记录数（条） | FIRMS 主动火点 CSV / Area API | 对筛选时间、区域内的观测记录计数 | 不等于独立火灾事件数，也不等于烧毁面积 |
| 烧毁像元数（个） | MCD64 `burndate` 或既有烧毁像元明细 | 对 `burndate > 0` 且落在选择区域的像元计数 | 不等于官方主动火点记录数 |
| 火烧迹地面积（km²） | MCD64 / 烧毁像元明细 | 对选中烧毁像元的实际地表面积求和 | 不等于 FIRMS `scan × track` 累计足迹 |

## 2. FIRMS 主动火点

系统支持两条真实数据链：

1. 导入已经下载的 FIRMS CSV；
2. 由后端调用 FIRMS Area API，按 `source + bbox + 日期范围` 下载 CSV。

若使用当前项目中的质量规则，则：

```text
VIIRS：confidence ∈ {n, h}
MODIS：confidence ≥ 30
```

这是质量筛选规则，不是秸秆焚烧识别规则。主动火点还可能是林火、居民点热源、工业热源或其他地表高温现象，是否属于秸秆焚烧需要额外的土地覆盖、作物分布、时空规则或人工复核。

FIRMS 的 Area API 是按边界框查询，返回的是卫星探测记录。密钥只应保存在后端环境变量 `FIRMS_MAP_KEY` 中，不应进入网页代码、截图、README 示例或 Git 提交记录。

## 3. MCD64 火烧迹地

对于月度 `burndate` TIF：

```text
burndate > 0  →  像元被产品判定为烧毁
burndate = 0  →  未燃烧
burndate < 0  →  非有效陆地或未制图等产品编码
```

文件名中 `AYYYYDDD` 表示该月起始年积日。例如 `A2026060` 对应 2026 年第 60 天，即 3 月 1 日。系统会检查正值是否落在相应月份的年积日区间，并将每一像元转换为实际烧毁日期。

当前 TIF 是经纬度（EPSG:4326）GeoTIFF。网格在不同纬度的地表面积不同，因此采用：

```text
面积 = R² × |Δλ| × |sin(φ北) - sin(φ南)|
```

其中 `R = 6,371,007.181 m`，经度差与纬度均转换为弧度。公式对所有已选择像元逐行计算并累加；不采用“每个像元固定 0.25 km²”的写法。

## 4. 当前资料的验证性结论

2026 年 3–5 月的三幅 MCD64 月度 TIF 已独立复算。以当时提供的五市边界为准，结果为：

| 月份 | 烧毁像元数 | 火烧迹地面积（km²） |
|---|---:|---:|
| 2026-03 | 1,140 | 187.3799 |
| 2026-04 | 47,918 | 7,773.6972 |
| 2026-05 | 16,794 | 2,702.3824 |

这些是 MCD64 火烧迹地统计结果，不应改写为“官方火点数量”。不同版本、来源、边界精度或去重规则的行政区边界会影响边缘像元归属；系统用导入的边界和导入批次保存这一前提。

## 5. 质量与误差提示

1. MCD64 对持续时间很短、面积很小的农田火烧斑块可能漏检；
2. 若未提供匹配的 `ba_qa` TIF，系统仅能记录“QA 未提供”，不能代替 QA 筛选；
3. FIRMS 的空间分辨率、过境时刻、云和观测几何会影响火点记录；
4. 只有加入秸秆地块或作物分布证据后，才可进一步做“疑似秸秆焚烧”筛查；首版不作该判断。
