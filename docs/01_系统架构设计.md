# 黑龙江省火点数据检测与风险评估平台

## 系统架构设计

### 1. 设计目标

系统采用面向本地计算环境的轻量化架构，在普通科研办公计算机条件下完成 FIRMS 主动火点数据和 MCD64A1 火烧迹地数据的处理。

系统设计重点包括：

- 保持软件能够独立运行；
- 控制硬件资源占用；
- 将数据处理算法与网页界面分离；
- 保证计算结果可追溯；
- 便于单元测试；
- 便于后续软件著作权说明书整理。

### 2. 技术架构

V1.0 采用以下主要技术：

- Python：主要开发语言；
- Flask：本地 Web 服务及用户界面接口；
- SQLite：本地结构化数据存储；
- Pandas / NumPy：表格和数值数据处理；
- GDAL / OGR：遥感栅格和矢量空间数据处理；
- HTML / CSS / JavaScript：用户界面；
- pytest：自动化测试。

V1.0 不依赖独立数据库服务器、消息队列或分布式计算系统。

### 3. 系统逻辑分层

系统划分为四个主要层次。

#### 3.1 Web 表现层

负责：

- 页面展示；
- 文件选择与上传；
- 用户参数输入；
- 任务状态显示；
- 统计结果显示；
- 地图展示；
- 成果下载。

Web 层不得直接实现遥感数据核心算法。

### 3.2 Services 业务层

负责组织完整业务流程，包括：

- 创建分析任务；
- 文件校验；
- FIRMS 数据导入；
- MCD64A1 数据导入；
- 统计计算；
- 风险评价；
- 成果导出；
- 任务状态管理。

Services 层负责调用 Core 和 Storage 层，但不重复实现底层算法。

### 3.3 Core 核心处理层

负责数据处理和计算算法。

主要模块包括：

- FIRMS 主动火点解析与质量筛选；
- MCD64A1 Burn Date 与 QA 解析；
- 行政区域空间匹配；
- 统计指标计算；
- 风险或关注等级计算。

Core 层应尽量保持与 Flask 页面无关，使核心算法可以独立测试。

### 3.4 Storage 数据存储层

负责：

- SQLite 数据库初始化；
- 数据表管理；
- 数据读写；
- 数据库版本迁移；
- 任务及结果持久化。

核心算法不应直接拼接大量 SQL 操作。

### 4. 分析任务业务流程

一次标准分析任务按照以下流程执行：

用户创建任务
→ 提交输入数据
→ 文件完整性检查
→ 数据格式校验
→ 记录文件身份信息
→ FIRMS 数据处理
→ MCD64A1 数据处理
→ 行政区域匹配
→ 统计分析
→ 风险或关注等级计算
→ 地图生成
→ 成果导出
→ 任务完成

任一阶段出现无法继续处理的错误时，应停止相关处理并记录错误原因。

可以继续处理但可能影响结果解释的问题，应记录为警告。

### 5. 数据存储原则

运行时数据与程序源码分离。

程序源码存储在 Git 仓库中。

用户上传数据、SQLite 数据库、日志和分析输出属于运行时数据，原则上不提交至 Git 仓库。

后续运行时目录统一规划在 `instance` 目录下。

主要运行数据包括：

- SQLite 数据库；
- 上传文件；
- 临时文件；
- 分析成果；
- 日志。

### 6. 主要核心模块

#### 6.1 FIRMS 模块

负责：

- CSV 解析；
- 字段检查；
- 时间标准化；
- 坐标检查；
- 质量筛选；
- 重复观测识别；
- 行政区域匹配；
- 标准化结果输出。

### 6.2 MCD64A1 模块

负责：

- Burn Date 栅格读取；
- QA 栅格读取；
- 栅格空间一致性检查；
- 有效烧毁像元识别；
- QA 条件筛选；
- 像元面积计算；
- 行政区域匹配；
- 标准化结果输出。

### 6.3 Statistics 模块

负责：

- 时间统计；
- 行政区域统计；
- FIRMS 数量统计；
- 火烧迹地面积统计；
- 综合指标整理。

### 6.4 Risk 模块

负责：

- 遥感火情相对关注程度评价；
- 外部规则型风险计算；
- 规则参数记录；
- 计算结果解释信息生成。

风险模块不得将无可靠来源的阈值包装为官方标准。

### 7. 可追溯设计

每个分析任务至少能够关联：

- 输入文件；
- 文件哈希；
- 输入产品类型；
- 数据时间范围；
- 处理参数；
- 数据质量规则；
- 行政边界版本；
- 软件版本；
- 输出结果；
- 处理日志。

同一个结果应能够追溯到对应分析任务。

### 8. 性能设计原则

针对普通个人计算机，V1.0 优先采用以下策略：

- FIRMS 表格采用分阶段处理，避免不必要的数据复制；
- MCD64A1 栅格尽可能按照块或窗口读取；
- 不长期将完整大型栅格全部保存在内存中；
- SQLite 采用批量写入；
- 地图展示不直接返回无限数量的点；
- 中间文件在任务结束后按照规则清理；
- 不引入非必要后台服务。

性能优化不得改变数据统计口径。

### 9. 测试原则

以下模块应具有自动测试：

- 数据库初始化；
- FIRMS 字段和质量筛选；
- FIRMS 去重；
- MCD64A1 Burn Date 解析；
- MCD64A1 QA 判断；
- 面积计算；
- 文件校验；
- 行政区统计；
- 风险计算；
- 主要 Flask API。

除自动测试外，每个正式版本还应进行至少一次完整业务流程测试。

### 10. 版本原则

`main` 分支原则上保存可以启动和运行的版本。

新功能采用独立开发分支。

开发完成后需要经过：

代码检查
→ 测试
→ 本地功能验证
→ Git 提交

再进入下一阶段。

任何尚未实现的规划功能不得在 README 或软件界面中标记为“已完成”。
